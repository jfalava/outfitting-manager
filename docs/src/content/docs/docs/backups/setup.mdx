Before setting up backups, check the [prerequisites](/docs/backups/prerequisites/). This guide covers Rustic, credentials, and profile configuration.

See the [backups CLI reference](/docs/cli/backups/) for command syntax and examples.

## Install Rustic

Install [Rustic](https://github.com/rustic-rs/rustic) 0.10 or later (with named backup selection) and put `rustic` on your `PATH`. To use a different executable, set `BACKUP_RUSTIC` to its path. The schedule generator requires absolute paths for both Rustic and the Outfitting Manager executable.

On Windows, optional per-job process guards use `powershell.exe`. The optional `secrets import-secretstore` command requires PowerShell 7 (`pwsh.exe`) with the SecretManagement and SecretStore modules installed.

```sh
rustic --version
```

## Store credentials

Use `backups secrets set` to enter credentials in a prompt. The CLI stores them in the OS credential store and supplies repository credentials to Rustic at run time; values are not accepted as command arguments or saved in your repository configuration.

- macOS: Keychain
- Windows: Credential Manager

Set these credentials on each machine:

| Secret                | Description                                                |
| --------------------- | ---------------------------------------------------------- |
| `access-key`          | Storage access key ID, such as an S3 or Cloudflare R2 key. |
| `secret-key`          | Storage secret access key.                                 |
| `repository-password` | Password that encrypts the Rustic repository.              |
| `alert-token`         | Bearer token for failure and review alerts.                |

Run `secrets check` after setting them. It verifies all four credentials, including the alert token.

```sh
outfitting-manager backups secrets set access-key
outfitting-manager backups secrets set secret-key
outfitting-manager backups secrets set repository-password
outfitting-manager backups secrets set alert-token
outfitting-manager backups secrets check
```

## Configure a backup profile

Backup profiles are separate from package profiles. Declare a profile in your `outfitting.json` manifest, then import it into the local `config.toml` with the configuration wizard. The profile selects Rustic TOML files; those files define the repository, jobs, source folders, and default retention. Outfitting can attach optional policies to those jobs. After import, local `config.toml` is authoritative; runtime does not reread the manifest.

### Declare the profile in `outfitting.json`

```json
{
  "schema": 3,
  "profiles": {
    "workstation": {
      "macos": { "nix": { "flake": "nix", "attribute": "workstation" } }
    }
  },
  "backups": {
    "defaultProfile": "personal",
    "profiles": {
      "personal": {
        "platform": "macos",
        "files": ["backups/common.toml", "backups/personal.toml"],
        "jobs": {
          "photos": { "retention": { "keep-monthly": 3 } }
        }
      }
    }
  }
}
```

Replace the package profile with your own declarations. The `files` paths are relative to the repository. Import the manifest and check the selected profile:

```sh
outfitting-manager config wizard \
  --manifest system/macos/outfitting.json
outfitting-manager backups doctor
```

For a local setup, use `schema = 2` and declare the same profile and policies in `config.toml`:

```toml
schema = 2

[backups]
profile = "personal"

[backups.profiles.personal]
platform = "macos"
files = ["backups/common.toml", "backups/personal.toml"]

[backups.profiles.personal.jobs.photos.retention]
keep-monthly = 3
```

### Select the standalone alert service

Configurations without alert settings keep posting the legacy backup payload to `https://backup-alert.jfalava.workers.dev/`. To opt in to the standalone service, set all three alert fields under the local `[backups]` table, alongside `profile`:

```toml
[backups]
profile = "personal"
alertUrl = "https://<approved-host>/v1/alerts/backups-jfa-mac-mini"
alertSender = "jfa-mac-mini@alerts.jfa.dev"
alertRecipient = ["backup-alerts@jfa.dev"]
```

The example selects the Mac machine identity. Windows uses the other row below. Both send to `backup-alerts@jfa.dev`:

| Machine | Endpoint path                     | `alertSender`                 |
| ------- | --------------------------------- | ----------------------------- |
| macOS   | `/v1/alerts/backups-jfa-mac-mini` | `jfa-mac-mini@alerts.jfa.dev` |
| Windows | `/v1/alerts/backups-jfa-windows`  | `jfa-windows@alerts.jfa.dev`  |

Use the full HTTPS endpoint from the approved `alert-worker` deployment output; the example host is not provisioned here. Only these two canonical paths are accepted, with no URL credentials, query, fragment, trailing slash, or encoded/path-normalized aliases. The selected profile's platform must match its machine route. The old `/v1/alerts`, `/v1/alerts/backups`, and per-job routes are not supported. This is local manager configuration, not an `outfitting.json` or Rustic setting. Wizard edits and manifest re-import preserve all three fields. Scheduled invocations read the same config file, so no extra scheduler environment variable is needed. Partial alert configuration fails validation; it never silently selects the legacy service.

All jobs on one machine share that machine's route and token; there are no per-job credentials, selector headers, or fan-out. Provision **different token values** for Mac and Windows. The native `alert-token` remains `rustic-backup-alert-token` under the scheduled user's account in each device's Keychain or Credential Manager. Equal native identity names on separate devices do not imply shared values. The existing interactive `outfitting-manager backups secrets set alert-token` command stays unchanged; do not put tokens in TOML or environment variables. Windows SecretStore import retains its existing identities and does not provision the new server credentials.

`alertSender` is one bare mailbox; `alertRecipient` contains 1–50 distinct bare mailboxes, all visible in the email's To field. The Worker currently allows only the machine sender in the table and the shared `backup-alerts@jfa.dev` recipient. Mailboxes use ASCII dot-atom local parts (up to 64 characters) and DNS domains (labels up to 63 characters), with at most 254 characters overall. Display names, whitespace, quoted local parts, domain literals, and non-ASCII addresses are rejected. Domain case is ignored for duplicate and allowlist checks, but local-part case is significant; the CLI preserves supplied case. Local validation checks syntax, counts, and duplicates, not the server's live allowlists. A syntactically valid address outside the configured allowlists still fails with 403.

The CLI sends `POST` to the configured machine endpoint with `Content-Type: application/json` and `Authorization: Bearer <alert-token>`. The JSON contains required `sender` and `recipient` (an array), `title`, `message`, `severity: "error"`, an ISO timestamp with `Z`, and `metadata: { hostname, operation, job }` for job failures or review-required candidates. The title puts the operation and job name before the hostname so a long hostname cannot truncate the job. Repository-wide/check failures use the **same machine endpoint and token**, with `metadata: { hostname, operation }` and no invented job name. The authenticated route identifies the machine; the job is descriptive, not an authorization boundary. An exit code is omitted because local validation failures do not always have one.

The CLI strips NUL from messages, keeps its existing 4,000 UTF-16-unit message cap, and bounds control-free titles to 200 UTF-16 units. It rejects serialized bodies over 32,768 actual UTF-8 bytes locally, including all addressing and metadata. Only HTTP 202 with `{ "sent": true, "message_id": "..." }` and a nonempty ID confirms provider acceptance, not inbox delivery.

Rejected responses never confirm acceptance: 400 indicates invalid payload, 401 authentication or disabled service, 403 an address outside the service allowlists, 404 a wrong route, 413 an oversized body, 415 unsupported encoding, 502 provider failure, and 503 unavailable service configuration or bindings. A 403 rejects the whole recipient list without sending any email. Fix configuration or provisioning rather than retrying rejected requests.

Cut over each host separately, with explicit approval for deployment, server secrets, and host changes:

1. Deploy the standalone service and obtain its endpoint. Independently provision the pinned credentials `ALERT_WORKER_BACKUPS_JFA_MAC_MINI_TOKEN` and `ALERT_WORKER_BACKUPS_JFA_WINDOWS_TOKEN` with distinct values, and the approved machine allowlists. The checked-in Worker desired state leaves both machine services disabled; activation is a separate approved change after provider/binding readiness is verified. The legacy Worker's secrets remain untouched. Do not rename or overwrite native credentials as part of installing this CLI.
2. For each machine service, send a controlled request with its provisioned credential and approved addressing after approved activation. Verify HTTP 202 and receipt of the email, and verify that the other machine's token is rejected. A successful health check or partial validation does not verify delivery. Do not deliberately fail a real backup for this test.
3. Pause scheduled invocations briefly. Set that machine's approved endpoint, sender, and recipient array together in local `config.toml`; explicitly update its `alert-token` through the native prompt if the token changes, retaining the old value securely for rollback. Verify the selected endpoint, addressing, and token before resuming the schedule. Repository credentials and backup receipts do not change. Earlier standalone configurations must replace the shared or unscoped URL with the correct machine route; no automatic migration writes host settings.
4. On rollback, pause scheduling, remove all three fields (`backups.alertUrl`, `backups.alertSender`, and `backups.alertRecipient`), restore the old token if it changed, then resume. Verify the old endpoint and credential still work before relying on rollback; a revoked legacy credential cannot be restored by this CLI. There is no automatic fallback from v1 to legacy after a rejection or timeout.

Requests have a 20-second timeout, no automatic retry, and no idempotency guarantee. A timeout can occur after provider acceptance; retrying manually or on a later failed backup may duplicate email. Alert errors only log a warning and never replace the backup result.

The legacy default exists only for staged cutover. Remove the legacy endpoint and payload branch once **every scheduled host** has a verified v1 endpoint/token pair and the rollback window is closed. Retiring the old Worker, its infrastructure state, or its secrets is a separate approved operation. Installing this CLI alone does not deploy the service, change any host configuration or credentials, or retire the old Worker.

### Configure the Rustic TOML files

The declared TOML files specify the repository, retention policy, and source folders.

The names `project-data` and `photos` below are examples, not defaults. Choose names for your own jobs; the source folders and policies determine what each job backs up and how it behaves.

```toml
[repository]
repository = "opendal:s3"

[repository.options]
bucket = "my-backup-bucket"
endpoint = "https://<account-id>.r2.cloudflarestorage.com"
region = "auto"

[forget]
keep-daily = 7
keep-weekly = 4
keep-monthly = 12

[[backup.snapshots]]
name = "project-data"
sources = ["/Users/your-user/Projects"]
tags = ["project-data"]
skip-if-unchanged = true

[[backup.snapshots]]
name = "photos"
sources = ["/Users/your-user/Pictures"]
tags = ["photos"]
skip-if-unchanged = true
```

Replace the source paths with your actual absolute folders.

Every `[[backup.snapshots]]` entry creates a job, in composition order. There is no built-in job list on either platform. Declare at least one snapshot with a unique name. Names use 1–64 lowercase ASCII letters, digits, `_`, or `-`, starting with a letter or digit. `check` and Windows device names such as `con` are reserved.

Use the snapshot's `name` in CLI job arguments and any matching `jobs` policy key. Tags must include that same name and must not include another configured job's name, commas, control characters, or surrounding whitespace. Other annotation tags can be shared.

### Attach optional job policies

The `jobs` map attaches policies to existing TOML snapshots; it does not create jobs. Unknown job references or policy fields are errors. Jobs without policies inherit `[forget]` and have no process guard.

- `retention` overrides `keep-daily`, `keep-weekly`, and `keep-monthly` individually. Omitted counters inherit the TOML default; `0` disables a counter and `-1` keeps all qualifying period representatives. Each job needs at least one enabled counter. Global `keep-id` pins and recovery anchors remain protected.
- `skipIfProcessesRunning` lists up to 32 exact Windows process basenames without `.exe`, paths, or wildcards. Matching ignores case. Names use letters, digits, `.`, `_`, or `-`, start with a letter or digit, and are at most 128 characters. Process guards are currently Windows-only; macOS rejects nonempty lists.

For a Windows profile with a `project-data` snapshot, add:

```toml
[backups.profiles.workstation.jobs.project-data]
skipIfProcessesRunning = ["ExampleEditor", "Editor_Helper"]
```

### Migrate an existing backup configuration

Backup declarations now require manifest schema 3 and local config schema 2. Older backup-bearing configurations are rejected rather than silently losing implicit policies. Configurations without backups remain readable.

Pause scheduled invocations during cutover. Preserve the existing job names, tags, repository configuration, hostname, credentials, and receipt directory. Before updating the schema versions, move any previous implicit behavior into explicit policies. For the former built-in Windows profile, the equivalent local policy is:

```toml
[backups.profiles.gaming-pc.jobs.ffxiv-configs]
skipIfProcessesRunning = ["ffxiv_dx11", "ffxiv", "ffxivlauncher", "XIVLauncher"]

[backups.profiles.gaming-pc.jobs.mmo-screenshots.retention]
keep-monthly = 3
```

These are historical job names, not required names for new profiles. Keep the names already associated with your snapshots and receipts when migrating.

Use your actual backup profile name instead of `gaming-pc`; declare the equivalent `jobs` map in the manifest if you import it. Then set manifest `schema` to 3 and local `schema` to 2. Re-importing replaces current-platform policies, while ordinary wizard edits preserve them. Refresh any remote source cache using the configuration wizard before offline scheduled runs. Run `backups doctor`, verify a backup without retention, and resume the schedule only after checking the results. Do not initialize the existing repository or discard its receipts.

## Run schedules with the right permissions

- The account running a backup needs read access to every source folder.
- Run the LaunchAgent or scheduled task as the same logged-in user who stored the credentials. On Windows, the user must remain logged in; a locked session is fine.
