`outfitting-manager backups` runs [Rustic](https://github.com/rustic-rs/rustic) with the selected backup profile and credentials from your OS credential store. It records each result locally and checks snapshots before accepting them.

See the [backups CLI reference](/docs/cli/backups/) for command syntax and examples.

## Run a backup now

`backups run` runs every named snapshot in the selected profile's composed Rustic TOML, in declaration order. Job names and counts are not built into the CLI. Use `--job` to run just one; unknown names are rejected before operations start. Neither `run` nor `run-due` applies retention or deletes snapshots.

Use `backups doctor` to see the selected profile's job names. The `project-data` job below is an example from the [setup guide](/docs/backups/setup/); use the `name` of a snapshot in your own profile.

```sh
# Back up all configured folders
outfitting-manager backups run

# Back up only one specific job
outfitting-manager backups run --job project-data
```

Rustic deduplicates unchanged data. If a snapshot uses `skip-if-unchanged = true`, it can also skip creating a new snapshot when its sources have not changed.

## Let the schedule catch up

Generated LaunchAgents and Windows Task Scheduler jobs call `backups run-due` hourly. The command starts each daily backup after local time reaches 10:00 on macOS or 09:00 on Windows. It also checks repository metadata after Sunday at 15:00, if a weekly check is due. A failed job stays due for the next invocation; a candidate marked `review-required` waits for manual acceptance.

`backups schedule` prints the LaunchAgent or Task Scheduler definition; it does not install it.

## When a snapshot needs review

The CLI rejects a backup that processes zero files. It marks a candidate `review-required` if either its processed file count or logical bytes drop by more than 50% from the last accepted snapshot. The candidate does not become a recovery point until you inspect it and accept that exact snapshot with `backups accept`.

On Windows, a job with `skipIfProcessesRunning` checks its configured process names before backing up. If any match, it skips only that job without changing its receipt or recovery anchors, leaving it due for the next run. The guard also applies to manual runs. A failed, malformed, or timed-out process check fails closed. Jobs without this policy have no process guard. This is a preflight check, not a guarantee that an application cannot start during the backup.

Failed backups and candidates that need review trigger a webhook alert.

A local lock prevents backup operations against the same repository from running at the same time.

## Preview and apply retention

`backups maintenance` previews which snapshots the retention policy would remove. It requires two accepted snapshots for every job and a successful backup within the last 48 hours. The two accepted snapshots for each job are protected from deletion.

Retention defaults come from Rustic `[forget]`; optional Outfitting per-job overrides replace individual counters. A snapshot must belong to only one configured job's identity tag. Ambiguous tags block retention, including when history is acknowledged.

Pass `--apply` to apply the retention policy and prune unused data. If the repository contains snapshots not recorded in local receipts, review them and pass `--acknowledge-history` before applying retention.

Adding a job starts fresh receipt history and blocks maintenance until it meets the same prerequisites. Removing a job stops its runs but does not remove receipts or snapshots. Receipts for removed jobs block `--apply` until their recovery anchors are explicitly reconciled; preview and inspection remain available. Renaming a job is removal plus addition, not an automatic history transfer. Profile names do not create separate receipt namespaces: jobs share receipts when repository, hostname, and job ID match. Changing sources under an existing ID requires reconciliation if they no longer match accepted anchors.

## Restore a snapshot

`backups restore` writes into a directory that does not exist yet. It refuses a destination that overlaps any configured backup source, so restore elsewhere and inspect the recovered files before relying on them.
